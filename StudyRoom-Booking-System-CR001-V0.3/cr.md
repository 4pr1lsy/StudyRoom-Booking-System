## 一、具体开发分工

### Member B：前端界面与交互开发

**负责目标：** 完成预约修改界面，以及取消预约自定义确认弹窗。

**主要负责文件：**

-   `records.html`
-   `js/app.js`
-   `css/style.css`

**具体工作：**

1.  在"我的预约"页面为本人有效且尚未结束的预约增加"修改预约"入口。
2.  实现预约日期、开始时间和结束时间的编辑界面；自习室和座位信息只展示，不允许在本次变更中更换。
3.  保存修改时调用 C 实现的
    `StudyStorage.updateBooking(booking.id, { date, start, end })`
    接口，不要在前端直接操作
    localStorage，也不要自行重复编写冲突判断规则。
4.  将浏览器原生 `confirm()`
    改为网页内的自定义确认弹窗，提供"确认取消"和"暂不取消"操作。
5.  操作成功后刷新页面显示；操作失败时展示清晰提示，不得误报成功。

**交付内容：** 修改后的前端文件、页面检查结果、必要截图和简要修改说明。

### Member C：预约业务逻辑与数据存储开发

**负责目标：** 完成已有预约的安全更新，保证预约数据正确保存。

**主要负责文件：**

-   `js/storage.js`
-   `tests/storage.test.js`

**具体工作：**

1.  实现 `StudyStorage.updateBooking(id, changes)`。
2.  `changes` 只允许包含
    `date`、`start`、`end`，不得通过该接口更改预约编号、用户、房间、座位或预约状态。
3.  只允许当前登录用户修改本人有效且尚未结束的预约。
4.  调用 D 提供的 `StudyCore.canUpdateBooking(...)`
    核心规则接口完成合法性及冲突检查。
5.  必须先完成全部校验，再更新并保存原预约记录；修改失败时原数据不得发生变化。
6.  补充存储层测试，覆盖成功修改、无权限修改、已取消或已结束预约、冲突修改以及失败后原数据保持不变等情况。

**交付内容：** 修改后的存储层文件、自动化测试结果和简要修改说明。

### Member D：预约核心规则与冲突检测开发

**负责目标：** 完成预约修改所需的核心合法性判断和冲突检测。

**主要负责文件：**

-   `js/core.js`
-   `tests/core.test.js`

**具体工作：**

1.  新增核心规则接口：

    `StudyCore.canUpdateBooking(bookings, bookingId, req, today, now)`

2.  检查目标预约是否存在、是否有效，以及是否已经开始或结束。

3.  检查修改后的日期和时间是否合法，包括日期范围、营业时间、开始时间与结束时间顺序等。

4.  检查修改后的时间是否与其他有效预约冲突。

5.  冲突检测必须排除当前正在修改的预约自身，避免把原预约误判为冲突。

6.  保持原有时间区间规则：相邻时段可以预约，已取消预约不占用座位。

7.  补充核心规则测试，覆盖正常修改、冲突、相邻时段、非法时间、当前预约自身排除等情况。

**交付内容：**
修改后的核心规则文件、自动化测试结果、接口说明和简要修改说明。

## 二、统一接口与协作顺序

三个人的代码需要配合，接口名称和参数必须保持一致：

-   **D 提供核心规则接口：**
    `StudyCore.canUpdateBooking(bookings, bookingId, req, today, now)`
-   **C 提供存储接口：**
    `StudyStorage.updateBooking(id, { date, start, end })`
-   **B 在前端调用存储接口：**
    `StudyStorage.updateBooking(booking.id, { date, start, end })`

建议按照以下顺序进行正式集成：

1.  D 先完成核心规则接口和测试，并提交 GitHub Pull Request。
2.  我审核并合并 D 的修改后，C 基于更新后的主分支完成存储层接口和测试。
3.  我审核并合并 C 的修改后，B 基于更新后的主分支完成前端调用和交互。
4.  三人各自完成后，我统一进行代码集成、自动化测试、浏览器功能回归和最终验收。

如果发现接口或原有代码结构与任务书不一致，请先在 GitHub Issue

## 三、GitHub 开发与提交方式

本次统一使用 GitHub
仓库进行代码协作。**不再通过群聊发送整包代码或把修改后的文件只交给我；每位成员都需要将自己的开发成果上传到
GitHub。**

### 1. 接受仓库邀请

我会邀请 B、C、D 加入私有仓库。请大家登录自己的 GitHub
账号，接受邀请，并确认能够打开仓库：

[StudyRoom-Booking-System](https://github.com/4pr1lsy/StudyRoom-Booking-System)

### 2. 在自己的开发分支中工作

不要直接在 `main` 主分支上修改或上传代码。每个人使用独立分支：

-   D：`feature/member-d-core-validation`
-   C：`feature/member-c-booking-storage`
-   B：`feature/member-b-booking-edit-ui`

创建分支时，以当时最新的 `main` 为基础。由于三人的接口存在依赖，D
的修改合并后，C 再从更新后的 `main` 创建自己的分支；C 合并后，B
再从更新后的 `main` 创建自己的分支。

### 3. 修改代码并上传到自己的分支

可以先从 GitHub 仓库下载当前代码 ZIP，在本地完成自己负责的开发和测试。

开发完成后：

1.  打开 GitHub 仓库，切换到自己的开发分支。
2.  进入需要更新的对应目录，例如 `js/`、`css/` 或 `tests/`。
3.  点击 `Add file` → `Upload files`。
4.  上传自己实际修改的文件，注意放回原来的目录位置。
5.  检查文件路径和文件内容无误后，填写清楚的提交说明（Commit
    message），例如 `Add booking update validation`。
6.  点击 `Commit changes`，确认提交目标是自己的开发分支，而不是 `main`。

**只上传自己负责且实际修改的文件，不要把整个项目重新上传一遍，也不要覆盖其他成员的文件。**
如果修改涉及多个目录，可以分别进入对应目录上传。

### 4. 创建 Pull Request，等待项目经理审核

代码上传到自己的分支后：

1.  打开仓库顶部的 `Pull requests`。
2.  点击 `New pull request`。
3.  `base` 选择 `main`，`compare` 选择自己的开发分支。
4.  标题写清楚任务，例如 `Member D: Add booking update validation`。
5.  在说明中写明完成内容、修改文件、测试情况和已知问题。
6.  创建 Pull Request，并通知我审核。

我会检查代码差异、接口和测试结果。审核通过后，由我合并到
`main`。**未经审核，不要自行把开发分支合并到 `main`。**

### 5. 每个人需要提交的成果

每位成员完成后，GitHub 上应当能够看到：

-   自己负责的代码文件修改；
-   对应的测试文件或测试结果；
-   清楚的 Commit 记录；
-   一个说明完整的 Pull Request；
-   对应任务的完成情况及遗留问题。
